# InsightPro 信息检索整改方案

**制定日期**：2026-10-22
**参考基线**：制定时的 InsightPro 工作区；[Daily_News `e96419a`](https://github.com/ZJM189/Daily_News/tree/e96419ae95f38993831295ca30c67bcc958010f9) 的信息库与检索能力。问题表保留制定时的代码现状，不代表 1.1.0 当前状态。

**执行状态（2026-10-27）**：本方案提出的官方 AI 应用搜索、跨域分页/计数、相关性排序、筛选和结果上下文已纳入 1.1.0；发布复核修正了社区分类计数返回字段。原验收门槛中的真实查询样本 P95 与人工相关性评估不在本次发布门禁内，仍需单独采样评估。

## 目标与范围

让用户在现有已入库数据中，稳定找到相关的技术项目、云方案、官方 AI 应用、友商动态和自己有权访问的工作台对象。保留现有 `/search` 和知识库入口：全局搜索找对象与原文，知识库语义检索找知识片段。两者共享明确的来源与权限说明，不新建一套资讯产品。

本轮仅涉及**检索语料、匹配、排序、筛选、分页、结果展示与检索验证**。不增加收藏、关注流、简报、数据源、采集任务、独立 worker、聊天入口或新的模型调用。

## 当前问题

| 问题 | 代码依据 | 用户影响 |
|---|---|---|
| 语料缺口 | `backend/routers/search.py` 查询 GitHub、云方案、友商、Requirement、Solution；已入库 `vendor_ai_applications` 尚未加入 | 官方 AI 应用在专题页可见，却无法从全局搜索找到 |
| 截断后分页 | 各数据域在 SQL 中先 `LIMIT 100`，之后才跨域去重、排序和分页 | 命中多时靠后的结果不可达；`total` 和类型计数只反映截断后的候选集 |
| 相关性弱 | 多词以 `ILIKE` 全部匹配，排序只按标题精确/前缀/包含程度，再按标题字母顺序 | 正文高度相关但标题不含词的结果靠后；时间与来源可靠性不参与排序 |
| 结果上下文不足 | `/search` 结果仅有类型、标题、来源、摘录、URL；页面没有来源日期 | 用户难判断条目何时发布或采集、是否值得打开 |
| 两种检索边界不清 | `/search` 是对象关键词搜索；`/knowledge` 是 `knowledge_chunks` 的向量检索，覆盖范围和更新节奏不同 | 用户可能误以为两处搜索的是同一份完整数据 |

社区页短时缓存的内容仍不作为全局搜索历史语料；当前搜索只收录已入库、可追溯的来源。

## 整改步骤

### P0 · 搜得到、数得准

1. **补齐官方 AI 应用**：在现有 `/api/search` 增加 `vendor_ai_applications` 类型，检索名称、厂商、能力、摘要、机会与原文片段；结果显示官方链接和可用的发布日期。前端增加对应类型筛选与卡片文案。
2. **修正跨域分页与计数**：把去重、匹配、排序、类型筛选、计数和 `LIMIT/OFFSET` 放在数据库查询范围内，或采用等价的可证明完整的查询方式。不能再用“每表先取 100 条”冒充全量结果数。沿用现有 PostgreSQL，不引入新搜索服务。
3. **守住权限**：Requirement 和 Solution 在候选集生成与计数时就按当前 `user_id` 限制；未登录用户的类型计数和结果均不能包含个人数据。保留当前 API 参数和响应字段，新增字段为可选。

**验收**：已入库 AI 应用可按名称和厂商查到；构造单类型超过 100 条的匹配样本时，`total`、类型计数、末页与页间去重正确；匿名用户看不到任何个人工作台条目。

### P1 · 排得对、看得懂

4. **统一相关性规则**：标题精确命中优先，其次标题前缀、标题/厂商包含、内容命中；同档位再按来源日期与稳定对象键排序。日期优先取来源发布日期，缺失时标为采集时间；不把采集时间冒充发布日期。先使用现有 PostgreSQL 查询和索引，在代表性数据上评估后再补必要索引。
5. **提供最少筛选**：沿用现有类型筛选，增加时间范围筛选；时间参数进入 URL，翻页与切换类型时保留查询条件。只筛选有明确日期的已入库对象，缺失日期时按清晰规则处理并在界面说明。
6. **补结果解释**：卡片显示来源、日期及日期依据、命中摘录；公开对象保留可追溯原文链接，个人对象进入站内详情。空结果提示如何缩短关键词或调整时间范围。

**验收**：同一查询重复请求的排序稳定；标题精确命中排在仅正文命中之前；筛选和分页组合不会丢条件；结果所示日期能追溯到数据字段。

### P2 · 用样本决定是否继续优化

7. **建立检索样本集**：从现有五类对象中选取至少 30 个真实查询，包含中文、英文、别名、多词、旧内容、已下线方案和权限隔离场景。记录预期对象、期望前几位结果与实际响应时间。
8. **评估语义补充**：只有样本显示关键词检索仍有明显漏召回时，再评估复用现有 `knowledge_chunks`/pgvector 做补充召回；先确认同步范围、用户权限和新鲜度，再决定是否与全局对象搜索合并。知识库现有语义入口继续保持其知识片段语义。

**验收门槛**：样本中已知目标至少 90% 出现在前 10 条；前 5 条相关性由人工抽样复核；代表性数据量下检索响应 P95 不超过 1 秒。门槛是整改目标，实施前先测当前基线，并记录无法达到的具体查询。

## 实施位置与兼容要求

| 位置 | 预计修改 |
|---|---|
| `backend/routers/search.py` | 检索语料、查询排序、计数、筛选、分页与返回字段 |
| `frontend/src/app/search/page.tsx` | AI 应用类型、时间筛选、来源日期与结果说明 |
| `frontend/src/components/search-bar.tsx` | 校对建议词与结果类型；保持现有快速搜索入口 |
| `backend/services/startup_service.py` 或 Alembic 迁移 | 仅在查询计划证明需要时补检索索引 |
| `backend/tests/test_search.py` | 覆盖多域分页、排序、日期与用户隔离等非平凡检索逻辑 |

不改现有收藏、任务、采集、Agent 或身份模型。若 SQL 重写涉及大量数据，先用当前数据量执行 `EXPLAIN` 和基线查询，再决定索引；避免为了一个页面引入独立搜索基础设施。

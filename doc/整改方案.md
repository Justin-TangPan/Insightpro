## 一、整改目标

当前项目已经具备前后端骨架、数据采集、AI 报告、邮件、埋点和多页面展示能力，但仍存在数据契约割裂、前端页面臃肿、后端 legacy 依赖、认证边界不足、仓库噪声过大等维护风险。

本轮整改目标不是增加新功能，而是把项目拉回可持续迭代状态：

1. 质量门禁稳定：后端测试、前端 lint、前端 build 可重复通过。
2. 数据契约稳定：数据库 schema、后端 SQL、前端类型逐步统一。
3. 模块边界清晰：router 只负责 HTTP，service 负责业务，repository 负责数据访问。
4. 安全边界明确：关键写操作和敏感操作必须有认证/权限保护。
5. 文档和版本同步：项目规则、README、版本记录与真实代码状态一致。
6. 部署可恢复：前后端由 Docker Compose 托管，服务器重启后自动恢复并通过健康检查。
7. 数据时效可信：实时页面只展示满足新鲜度 SLA 且能追溯来源的数据，过期或降级必须明确标识。

## 四、执行阶段

### Phase 0：生产部署与开机自启

状态：**Docker 生产迁移已完成（2026-07-13）**。前后端已迁移为非 root 容器，Docker daemon 开机自启、`unless-stopped` 重启策略、容器健康检查、端到端自愈定时器和失败回退发布脚本均已落地。旧 systemd 应用服务保留作为回退，已禁用避免端口冲突；HTTPS 代理仍为后续加固项。

目标：服务器重启后，前端 `0.0.0.0:3000` 和后端 `0.0.0.0:8000` 自动恢复；发布与开机启动相互独立。

当前实现：

- `backend/Dockerfile` 使用 Python 3.11 slim，`frontend/Dockerfile` 使用 Next.js standalone 多阶段构建，运行时均为 UID/GID 10001。
- `compose.yaml` 创建独立网络，前端通过 `http://backend:8000` 同源代理 API，继续映射 `0.0.0.0:3000/8000`。
- Docker daemon 已 enabled/active，容器使用 `restart: unless-stopped`；开机不执行 npm/pip 或联网构建。
- `scripts/deploy-docker.sh` 在切换前执行测试、lint 和镜像构建，新容器未通过端到端验收时自动回退 systemd 旧部署。
- `insight-docker-health-guard.timer` 每 10 分钟处理容器/代理故障和数据补跑。

历史 systemd 阶段动作（仅作回退保留）：

- 建立独立 Linux Python 虚拟环境，禁止继续依赖全局 Python 包。
- 增加 `insight-backend.service`：从 `backend/` 启动 `uvicorn main:app --host 0.0.0.0 --port 8000`。
- 增加 `insight-frontend.service`：在已完成生产构建的前提下启动 `next start --hostname 0.0.0.0 --port 3000`。
- 增加 `insight-web.target`，统一启停两个服务；依赖 `network-online.target`，配置 `Restart=always` 和启动频率限制。
- 增加 `scripts/deploy.sh`：依赖安装、测试、lint、build 全部成功后才重启服务；开机时不执行 `npm ci` 或联网下载依赖。
- 使用 journald 或固定日志目录，配置日志轮转；停止使用仅适配 Windows 的 PowerShell 看门狗作为 Linux 主方案。
- 后续迁移到专用非 root 用户和 `/opt/insight-web`，再由 Nginx/Caddy 提供 HTTPS 和同源 `/api` 代理。

验收：

- `systemctl enable insight-web.target` 已生效。
- 重启服务器后两个端口自动监听，前后端健康检查均返回 200。
- 人为终止任一进程后，systemd 能自动拉起且不会出现重启风暴。
- 发布失败时旧版本继续运行，不留下半构建版本。

目标：技术热点、行业、政策、厂商、招标、需求等实时洞察均可证明“数据来自哪里、何时采集、是否过期”，不再使用旧静态内容填充实时页面。

#### 根因

1. APScheduler 仍嵌在单一 Web 进程中；数据任务已有启动补跑，邮件任务每分钟按订阅者排期检查。扩展到多 API 副本前需增加数据库租约。
2. 调度器使用内存状态，没有持久化 job store、最后成功时间、misfire 补偿、分布式锁或失败告警。
3. `/api/github-trending/business-eval` 在数据库查询成功但结果为空时直接返回空数组，仅数据库异常时才实时计算。
4. 新闻、政策、机会等页面存在前端硬编码数组；首页在 API 模块为空时保留静态 fallback，掩盖采集故障。
5. 数据源只有“能否返回内容”检查，没有发布日期、编码、标题质量、重复率、源覆盖率和链接有效性门禁。

#### 整改动作

- 将采集、AI 评估、需求派生、邮件发送从 Web 进程迁到独立 scheduler/worker；每次任务记录 `scheduled_at`、`started_at`、`finished_at`、`source_max_time`、数量、错误和重试次数。
- 服务启动时执行新鲜度巡检：当天关键任务缺失则按依赖顺序补跑，使用 `task_type + business_date` 幂等键防止重复。
- 定义数据 SLA：GitHub/热搜不超过 30 分钟，新闻/厂商不超过 6 小时，政策/招标不超过 24 小时；超时后页面显示“数据已过期”，不允许静默复用旧结论。
- 修复技术评估空结果逻辑：当天无评估记录时实时生成或进入队列，并返回明确的 `pending/degraded` 状态；不能返回 `source=database,count=0` 假装正常。
- 为所有 API 统一返回 `source`、`source_url`、`source_published_at`、`collected_at`、`freshness_status` 和 `quality_score`。
- 替换或修复失效源：财联社 404 API、36氪和一财空结果必须使用稳定官方接口/RSS或经过验证的新解析器；无法稳定获取时移出生产数据源。
- 招标优先使用中国政府采购网可验证详情页，解析真实发布时间、采购方、预算和绝对 URL；禁止用“某集团”“综合来源”模板作为实时招标。
- 删除商业快讯实时页的五月硬编码内容；政策和增长机会改为“最新事实数据 + 带证据时间的分析快照”，静态行业知识只能进入单独的基线知识库。
- 建立源级监控看板和告警：连续两次为 0、最新发布时间超 SLA、乱码率超阈值、链接失效率超阈值时告警并降级该源。

验收：

- 技术洞察当天有实时项目和评估结果；AI 不可用时明确显示启发式降级，不出现无解释空白。
- 任意服务停机一天后重新启动，关键数据能自动补跑到当天且不会重复写入。
- 页面上的“实时”标签只在数据满足 SLA 时出现，所有卡片都能追溯到具体原文和发布时间。
- 36氪、一财、财联社、政策、厂商、招标各源都有自动化解析样本测试和每日新鲜度检查。

### Phase 7：端到端可用性与自愈

状态：**第一阶段已完成（2026-07-13）**。健康标准已从“端口能返回 200”升级为“浏览器同源代理、数据库、新鲜度、当日热点与技术评估全链路正常”，systemd 定时巡检与自愈已上线。

目标：防止“服务活着但页面空白”再次被当成正常，并将可自动处理的故障从人工操作中移除。

已落地：

- `/api/system/health/live` 只判定进程存活；`/api/system/health/ready` 检查 PostgreSQL、九类数据新鲜度、当日 GitHub 日榜和技术评估数量。
- `scripts/health-check.sh full` 同时经过 8000 直连和 3000 同源代理，并验证技术评估页面所用的 JSON 契约非空。
- `insight-health-guard.timer` 每 10 分钟巡检：进程/代理故障由 systemd 重启，数据故障调用幂等补跑，修复有一小时冷却防止重试风暴。
- 持续故障写入 journald；如配置 `INSIGHT_ALERT_WEBHOOK`，会同时向告警 Webhook 发送消息。
- 部署门禁改用完整端到端检查，不再以首页 200 作为发布成功依据。

后续加固：

- 将可选 Webhook 对接到实际使用的飞书/企微/邮件告警通道。
- 增加真实浏览器 E2E，监测 React 渲染后的卡片数量和前端运行时错误。
- 将采集任务状态持久化，补齐源级失败次数、耗时、入库量和最新原文时间指标。

## 五、执行纪律

1. 每次整改只解决一个明确问题域，避免大范围视觉和业务重构混在一起。
2. 每轮结束必须运行：

```bash
cd frontend && npm run lint && npm run build
cd .. && pytest -q backend/tests
python -m py_compile backend/main.py backend/routers/*.py backend/services/*.py backend/main_legacy.py backend/crawlers.py backend/db.py backend/settings.py backend/deep_searcher_integration.py
```

3. 每轮结束必须更新 `log/versions.md`。
4. 不提交 `.env`、日志、数据库、本地缓存、构建产物。
5. 对无法立即修复的问题，记录在版本日志“已知遗留”中。

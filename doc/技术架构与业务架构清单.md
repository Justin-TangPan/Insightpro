# InsightPro 技术架构与业务架构清单

**基线日期**：2026-08-29

**产品定位**：AI 驱动的技术解决方案洞察与决策工作台

**事实来源**：当前前后端代码、Prisma schema、Compose 配置及已部署环境

## 1. 业务架构

### 1.1 产品边界

InsightPro 处理五类核心对象：

1. 开源技术项目：发现技术趋势并评估企业应用价值。
2. 云厂商技术解决方案：识别目录新增、内容变化和落地用途。
3. 云产品动态：用于交叉验证方案方向和厂商能力变化。
4. Requirement：从洞察或人工输入形成的用户技术需求。
5. Solution：用户自行管理、可关联多个 Requirement 的技术方案；与外部 `aliyun_solutions` 隔离。

平台输出是技术选型线索、方案理解和可追溯分析，不替代采购决策、合规审查或正式架构评审。

### 1.2 用户与价值

| 角色 | 主要任务 | 平台交付 |
|---|---|---|
| 解决方案架构师 | 发现可复用技术、理解部署路径、比较厂商能力 | 热点、方案目录、变化摘要、专题研报 |
| 技术负责人 | 判断成熟度、集成复杂度和落地适配度 | AI 价值评估、关键指标、风险建议 |
| 平台运营人员 | 管理采集、数据状态和订阅分发 | 刷新操作、健康状态、邮件计划、访问数据 |
| 订阅接收人 | 定期获取重点变化 | 按星期与时间投递的邮件简报 |

### 1.3 业务能力清单

| 一级能力 | 二级能力 | 数据输入 | 主要输出 |
|---|---|---|---|
| 技术发现 | 日/周/月榜、历史回看、项目速读 | GitHub Trending、项目 README | 热点列表、用途摘要 |
| 技术评估 | 四维评分、等级、建议、推理 | 热点项目、AI 接口 | 技术业务价值评估 |
| 方案洞察 | 官方一级/二级目录、每日差异、存量基线、摘要 | 阿里云解决方案目录及详情 | 新增置顶、更新/下线统计、价值简介 |
| 需求工作台 | 创建、编辑、删除、状态筛选、来源追溯 | 外部洞察或人工输入 | Requirement 详情与关联方案 |
| 方案工作台 | 创建、编辑、删除、版本与分类管理 | Requirement、参考链接 | 自有 Solution 与相关需求 |
| 友商验证 | 厂商动态采集、厂商聚合、能力对照 | AWS、Azure、阿里云、腾讯云、火山云官网 | 最新动态、厂商摘要 |
| 分析生成 | 自定义分析任务、基线报告、归档 | 关键词、现有热点和方案数据 | 结构化深度研报 |
| 知识访问 | 首页聚合、多关键词相关性搜索、分类筛选、AI 问答 | PostgreSQL 当前数据及个人 Workbench | 看板、高亮搜索结果、对话回复 |
| 内容分发 | 邮件预览、定时发送、单人发送 | 当日核心数据、订阅计划 | HTML 邮件简报 |
| 平台治理 | 登录、管理员权限、埋点、健康与新鲜度 | Supabase Auth、运行日志、业务表 | 权限控制、状态与统计 |

百度热搜目前只作为辅助采集与新鲜度检查数据，不属于核心页面能力。

### 1.4 核心业务流程

```text
外部技术源
   │
   ▼
采集与质量过滤 ──► 去重 / 内容指纹 ──► PostgreSQL
                                              │
                    ┌─────────────────────────┼──────────────────────┐
                    ▼                         ▼                      ▼
              AI 摘要与评分              搜索 / 问答上下文       新鲜度与健康判定
                    │                         │                      │
                    └──────────────┬──────────┘                      │
                                   ▼                                │
                         首页 / 专题 / 研报 / 邮件 ◄────────────────┘
```

日常闭环：09:00 采集热点、方案和云产品动态，09:02–09:04 完成友商刷新、技术评估与用途摘要；服务错过计划时间时由启动补跑按依赖顺序恢复。

用户工作闭环：`Insight → 使用 Insight-Agent 分析 → Requirement Draft → Solution Draft → 持续跟踪`。对象上下文由 Backend 的 Context Service 归一化，Agent 只读取已授权的 Session Snapshot；任何业务写入均经用户确认后由 Workbench Service 执行。

### 1.5 业务规则与指标

| 项目 | 当前规则 |
|---|---|
| 方案变化 | 初次全量采集设为普通基线；此后以 URL 唯一标识、内容哈希比较上一版，新增置顶、变化标记更新、未再次出现的方案记录下线时间 |
| 技术评估 | 每日最多 25 个项目；AI 不可用时保留启发式结果并明确来源 |
| 报告 | 登录用户创建、读取和删除；结果持久化到 `insight_tasks` |
| 邮件 | 仅管理员维护订阅；星期使用 `0–6` 表示周一至周日，时间使用 `HH:MM` |
| 数据时效 | 热点、技术评估、方案和热搜要求当天；云产品与友商动态允许最多 1 天 |
| 就绪条件 | 数据库可用、全部数据集满足时效、当日热点和评估均非空 |

建议持续观察的产品指标：当日热点数、当日评估覆盖率、活跃方案数、近 7 日方案变化数、厂商动态新鲜度、报告成功率、邮件投递成功率和页面 UV/PV。当前系统已采集基础数量与访问数据，但尚未建立独立 KPI 告警阈值。

## 2. 技术架构

### 2.1 逻辑架构

```text
浏览器
  ├─ Next.js 16 / React 19 (:3000)
       ├─ App Router 页面、Supabase SSR、图表、Insight-Agent Shell
       └─ /api/* 同源 rewrite
            └─ FastAPI / Uvicorn (:8000)
                 ├─ routers：HTTP 契约与权限边界
                 ├─ services：业务规则、方案、AI、邮件、健康与补跑
                 ├─ repositories：Workbench PostgreSQL 数据访问
                 ├─ crawlers / main_legacy：外部采集及现存任务实现
                 ├─ APScheduler：单实例内嵌调度
                 └─ Supabase PostgreSQL
  └─ Insight-Agent Auth Gateway (:4096)
       ├─ 60 秒一次性 ticket → 30 天 HttpOnly Gateway Session（登出立即撤销）
       ├─ Runtime Manager → Hermes Agent 原生 Dashboard（仅内部网络）
       └─ 独立 insight-hermes Compose、配置和 Git Workspace

外部依赖：GitHub、阿里云、五家云厂商官网、百度、OpenAI 兼容 AI、SMTP、Supabase Auth
```

### 2.4 数据架构

PostgreSQL 是业务数据的唯一持久化存储，共 17 张 public 表：

| 数据域 | 表 |
|---|---|
| 技术热点 | `github_trending`、`trending_business_eval` |
| 解决方案 | `aliyun_solutions` |
| 工作台 | `requirements`、`solutions`、`requirement_solutions` |
| 云产品动态 | `cloud_vendor_news`、`competitor_news` |
| 辅助采集 | `baidu_hotsearch`、`scrape_log` |
| 分析交付 | `insight_tasks`、`email_subscribers` |
| 使用分析 | `page_visits` |
| Insight-Agent SSO（历史表名） | `opencode_sso_tickets`、`opencode_sso_sessions` |
| Context Bridge | `agent_sessions`、`agent_actions` |

Hermes Agent 的单数据目录不允许被多个并发实例共享。Insight-Agent 在 Gateway 后按稳定 `user_id` 路由到独立 Hermes 子进程、Linux UID、Workspace 和 `HERMES_HOME`；普通用户互不可见，管理员可通过受控目标 Ticket 管理各用户空间。公共知识库普通用户只读、管理员读写。`agent_sessions` 保存结构化 Context Snapshot；Runtime 仅通过内部受控 API 取得该 Snapshot 并同步到隔离 Workspace，不能访问 PostgreSQL。

Supabase Auth 用户位于认证系统中，不在 public schema 建表。字段、索引和唯一约束见 [数据库契约](database-schema.md)。系统不再依赖向量数据库；问答上下文直接从 PostgreSQL 检索。

| 时间 | 任务 | 结果 |
|---|---|---|
| 03:00 | 历史数据清理 | 控制数据体量 |
| 09:00 | GitHub Trending | 热点入库 |
| 09:00 | 阿里云解决方案 | 目录及变化状态入库 |

### 2.7 安全、可靠性与运维

| 领域 | 当前实现 |
|---|---|
| 身份 | Supabase Auth；写操作要求登录；邮件管理要求管理员 |
| 网络 | 浏览器使用 Next.js 同源代理；后端 CORS 使用环境变量白名单 |
| 密钥 | `.env` 注入，不进入镜像和仓库 |
| 容器 | 前后端均以 UID/GID 10001 非 root 运行，日志轮转 10 MB × 3 |
| Insight-Agent 隔离 | UID/GID 10002、只读根文件系统、独立可写 Workspace、禁用 bash/task/外部目录、全部 capabilities 移除；1.5 CPU、2 GiB 内存、512 PID、20 GiB 预算 |
| 健康 | liveness 只检查进程；readiness 检查数据库、时效和当日核心数据 |
| 恢复 | Compose restart、systemd 每 10 分钟巡检、启动补跑、发布失败回退 |
| 并发 | 调度任务限制 `max_instances=1`；启动补跑用 PostgreSQL 锁 |
| 质量门禁 | 后端 pytest；前端 ESLint、Prisma validate、Next build；端到端 full health |

### 2.8 已知限制与扩展触发条件

| 当前限制 | 影响 | 何时处理 |
|---|---|---|
| APScheduler 内嵌单个 API 进程 | 不支持直接横向扩容调度器 | 部署第二个后端副本前拆独立 worker 或增加数据库租约 |
| 报告使用 FastAPI `BackgroundTasks` | 进程重启可能中断正在执行的任务 | 报告量或可靠性要求提升时接持久化任务队列 |
| 上下文检索为关键词匹配 + 近期回退 | 不具备真正语义召回 | 可量化证明召回不足时再引入全文/向量索引 |
| 友商基准包含人工维护的静态字段 | 可能随时间失真 | 建立可验证来源与更新时间后替换静态字段 |
| 生产端口直接暴露 | 缺少统一 HTTPS 边界 | 对公网正式服务前增加 Nginx/Caddy 与证书 |
| 无浏览器 E2E 监测 | 无法自动发现渲染级故障 | 页面成为关键业务入口时补最小 E2E |
| 镜像仅保存在本机 | 新服务器恢复依赖现场构建 | 进入多环境发布时接企业镜像仓库 |
| Insight-Agent 当前使用 IP + 4096 临时入口 | SSO Gateway 具备访问门禁，但 HTTP 下 Cookie 暂不能设置 Secure | 准备域名后迁移到独立子域名和 TLS，并启用 Secure Cookie |

# InsightPro 运维手册

**基线日期**：2026-08-31

**生产方式**：InsightPro Docker Compose 双容器 + 独立 Insight-Agent Runtime Compose project

**时区**：Asia/Shanghai

## 1. 运行架构

| 服务 | 镜像 | 端口 | 健康检查 |
|---|---|---|---|
| `insight-frontend` | `insight-web-frontend:0.6.2` | `0.0.0.0:3000` | 经同源代理访问后端存活探针 |
| `insight-backend` | `insight-web-backend:0.6.2` | `0.0.0.0:8000` | `/api/system/health/live` |
| `insight-hermes-gateway` | `nginxinc/nginx-unprivileged:1.29.4-alpine` | `0.0.0.0:4096` | `/healthz` |
| `insight-hermes` | `insight-hermes:v2026.8.19` | 仅独立 Docker 网络 | Runtime `/healthz` |

InsightPro 两个核心容器通过 `insight-network` 通信，以 UID/GID 10001 非 root 运行，日志轮转为 10 MB × 3。PostgreSQL、Supabase Auth、AI 和 SMTP 是外部服务，不在 Compose 内运行。

Hermes Agent 与 Gateway 不加入 `insight-network` 和根目录 Compose，使用独立的 `insight-hermes-network`、持久化目录及 systemd unit；其故障不参与 InsightPro readiness 和 full health。

## 2. 首次部署

1. 安装 Docker 与 `docker-compose`。
2. 在仓库根目录创建 `.env`，至少配置 Supabase/PostgreSQL；按需配置 AI、SMTP 和告警 Webhook。
3. 使用 Docker Engine 28.5.2+ 验证 Compose 配置并启动：

```bash
docker-compose -p insight-web -f compose.yaml config
docker-compose -p insight-web -f compose.yaml up --detach --build
./scripts/health-check.sh full
```

4. 如需开机自愈，安装仓库中的 Compose systemd unit 与 timer；标准发布脚本会自动安装健康守护配置。

## 3. 标准发布

```bash
sudo ./scripts/deploy-docker.sh
```

发布门禁实际顺序：

1. 获取 `/run/lock/insight-web-docker-deploy.lock`，阻止并发发布。
2. 校验 Docker 与 Compose 配置。
3. 执行后端 pytest。
4. 执行前端 ESLint。
5. 构建前后端镜像；Next.js 生产构建在镜像阶段完成。
6. 安装 Docker 健康守护 unit，停用历史原生 systemd 应用服务。
7. 切换 Compose 容器并最多等待 180 秒。
8. `health-check.sh full` 通过后启用每 10 分钟健康守护。
9. 切换后失败则停止 Compose，并恢复历史 systemd 部署作为回退。

发布前如需显式校验 Prisma：

```bash
cd frontend && npx prisma validate
```

### Insight-Agent 独立服务

Insight-Agent Runtime 不属于 `insight-web` Compose project，主系统发布、回滚、健康守护和 `--remove-orphans` 不会管理它。

```bash
sudo ./deploy/hermes/manage.sh start
sudo ./deploy/hermes/manage.sh status
sudo ./deploy/hermes/manage.sh health
sudo ./deploy/hermes/manage.sh logs
sudo ./deploy/hermes/manage.sh restart
sudo ./deploy/hermes/manage.sh stop
sudo ./deploy/hermes/manage.sh upgrade
```

systemd unit 为 `insight-hermes.service`。运行时配置位于 `/etc/insight-hermes/hermes.env`；Gateway 密钥及后端只读副本位于同目录。Session、配置和独立 Git Workspace 位于 `/var/lib/insight-hermes/`。Workspace 不得出现生产 `.env`，不得挂载生产目录或 Docker Socket。

当前没有域名和 HTTPS。`/insight-agent` 与右下角入口使用站内原生对话界面；Gateway 临时地址 `http://159.138.89.233:4096` 仅供隔离 Hermes Workspace Runtime 使用。准备域名后改用独立 HTTPS 子域名并设置 `OPENCODE_COOKIE_SECURE=true`。

Runtime Manager 按 Supabase `user_id` 为每位用户建立独立 Hermes Dashboard 子进程、Linux UID、Workspace 和 Session 目录。普通用户仅能访问自己的空间并只读公共知识库；管理员可管理目标用户空间。Terminal 等高风险工具禁用，容器不挂载生产仓库、生产 Secret 或 Docker Socket。

## 4. 健康标准

### `infra`

```bash
./scripts/health-check.sh infra
```

检查：后端存活、前端首页返回、浏览器侧同源 `/api` 能访问后端。

### `full`

```bash
./scripts/health-check.sh full
```

在 `infra` 基础上检查：

- 后端及前端同源 `/api/system/health/ready` 均为 `healthy`。
- PostgreSQL 可连接。
- 六类监控数据集满足新鲜度。
- 当日 GitHub 热点与技术评估非空。
- 技术评估 JSON 包含项目名和等级。

探针职责：

| 探针 | 含义 | 失败处理 |
|---|---|---|
| `/api/system/health/live` | API 进程仍可响应 | 重启/重建容器 |
| `/api/system/health/ready` | 数据库与核心数据可服务 | 先补跑，再判断是否重建 |
| `/api/data/freshness` | 每类数据的最新日期和 SLA | 定位具体数据源 |

## 5. 日常操作

```bash
# 状态
docker-compose -p insight-web -f compose.yaml ps

# 日志
docker-compose -p insight-web -f compose.yaml logs --tail 100
docker-compose -p insight-web -f compose.yaml logs -f backend

# 重启
docker-compose -p insight-web -f compose.yaml restart

# 重建
docker-compose -p insight-web -f compose.yaml up --detach --build --remove-orphans

# 停止
docker-compose -p insight-web -f compose.yaml down

# 端到端验收
./scripts/health-check.sh full
```

生产机为 Huawei Cloud EulerOS 2.0，系统仓库只提供 Docker 18.09，因此当前通过官方静态二进制运行 Docker 28.5.2：版本目录 `/usr/local/lib/docker-28.5.2`，systemd drop-in `/etc/systemd/system/docker.service.d/20-insight-docker-28.conf`。升级时安装新版本目录并切换 drop-in；回滚时删除 drop-in、执行 `systemctl daemon-reload && systemctl restart docker` 即恢复系统 RPM 版本。`/var/lib/docker` 不随版本切换删除。

## 6. 调度与补跑

后端内嵌 APScheduler：

| 时间 | 任务 |
|---|---|
| 03:00 | 历史数据清理 |
| 09:00 | GitHub、阿里云/华为云解决方案目录、云厂商动态 |
| 09:02 | 友商动态 |
| 09:03 | 技术价值评估 |
| 09:04 | 项目用途摘要 |
| 每分钟 | 到期邮件检查 |

启动补跑顺序：GitHub → 阿里云/华为云解决方案目录 → 百度热搜 → 云厂商动态 → 友商动态 → 技术评估 → 缺失的项目摘要。当天已有数据则跳过，PostgreSQL advisory lock 防止多个进程同时补跑。

手动修复数据新鲜度：

```bash
docker-compose -p insight-web -f compose.yaml exec backend python maintenance.py repair-freshness
```

手动刷新 API 属于写操作，需携带登录用户 Bearer token；不要在公开脚本或日志中保存 token。

## 7. 开机自愈

```text
系统启动
  └─ docker.service
       └─ insight-docker-compose.service
            └─ down --remove-orphans + up --detach

insight-docker-health-guard.timer（开机 2 分钟后，随后每 10 分钟）
  ├─ full healthy：退出
  ├─ infra 失败：重建容器与网络
  └─ infra 正常、full 失败：执行幂等数据补跑
```

旧 Docker Engine 在 daemon 重启后可能保留失效网络引用，因此 Compose systemd unit 会先清理再重建，不只依赖 `restart: unless-stopped`。

```bash
systemctl is-enabled docker insight-docker-compose.service insight-docker-health-guard.timer
systemctl status insight-docker-health-guard.timer
journalctl -u insight-docker-health-guard.service -n 50 --no-pager
systemctl start insight-docker-health-guard.service
```

## 8. 告警

根目录 `.env` 可配置：

```dotenv
INSIGHT_ALERT_WEBHOOK=https://your-domain.example/webhook
```

持续故障时健康守护向该地址 POST `{"text":"消息内容"}`。Webhook 未配置时仍写入 journald。

## 9. 故障定位

### 容器未运行或反复退出

```bash
docker logs insight-backend --tail 100
docker logs insight-frontend --tail 100
docker-compose -p insight-web -f compose.yaml down --remove-orphans
docker-compose -p insight-web -f compose.yaml up --detach
```

常见原因：旧网络引用、3000/8000 端口冲突、`.env` 缺失、外部数据库不可达。

### 页面可打开但没有数据

```bash
curl -fsS http://127.0.0.1:8000/api/system/health/ready | python3 -m json.tool
curl -fsS http://127.0.0.1:8000/api/data/freshness | python3 -m json.tool
./scripts/health-check.sh full
```

根据 `failed_checks` 和具体 dataset 判断是数据库、采集源还是评估数据问题；基础设施正常时优先执行补跑，不要先重建数据库。

### 前端同源 API 失败

```bash
curl -f http://127.0.0.1:8000/api/system/health/live
curl -f http://127.0.0.1:3000/api/system/health/live
docker logs insight-frontend --tail 100
```

直连成功而同源失败时，检查 `API_PROXY_TARGET=http://backend:8000` 和 `insight-network`。

### AI 或邮件失败

- AI：检查 `CHAT_API_URL`、`CHAT_API_KEY`、`CHAT_MODEL` 及供应商响应；不输出密钥。
- 邮件：检查 SMTP 主机、端口、授权码、发件人和管理员权限；先用邮件预览，再向单个订阅者测试。

## 10. 备份、回滚与变更纪律

- 业务数据位于外部 Supabase PostgreSQL，容器重建不会备份数据库。
- 执行列删除、表删除或类型迁移前必须单独备份并核对目标。
- 发布失败的自动回退只恢复应用运行方式，不回滚数据库变更。
- `.env`、token、数据库口令和完整用户数据不得进入日志、截图或版本库。
- 当前未配置 HTTPS 反向代理、远程镜像仓库和浏览器 E2E；使用场景达到相应触发条件后按 [改进清单](整改方案.md) 处理。
